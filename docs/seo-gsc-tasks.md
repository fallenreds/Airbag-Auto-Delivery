# SEO: задачи по отчёту Google Search Console

Ресурс `sc-domain:airbagad.com`, отчёт «Индексирование страниц» на 10.08.2026.
Вне индекса **3 383 адреса** по десяти причинам.

Визуальная версия документа: https://claude.ai/code/artifact/2edb9269-7694-4273-9626-bac871319716

Каждая задача описана одинаково: **Проблема** — что именно сломано и чем это подтверждается,
**Как влияет** — что теряет сайт, **Как лечить** — конкретные шаги, **Проверка** — признак,
по которому видно, что задача закрыта.

Сделано в ветке `fix/seo-indexing` сабмодуля `frontend` (коммит `0c4614b`), **ожидает
выкладки**: **T-1, T-3, T-4, T-6, T-8, T-10**. **T-5 снята как ложная находка.**

**T-2 выкатан 10.08.2026** — nginx перенастроен, проверено снаружи: `www` отдаёт 301 на
основной домен за один хоп (и с HTTP, и с HTTPS), корень отвечает 301 на `/uk/`, ACME

Осталось: **T-7** (переводы каталога), **T-9** (политика для снятых товаров + признак
публикации в API), **T-11** (диагностика в интерфейсе GSC), **T-12** (повторный замер

# P0

## T-1. Настроить 301-редиректы со старых адресов WooCommerce
**780 URL**

**Проблема.** При переезде на Next.js адреса сменились с `/product/…` на `/{локаль}/product/…`,
редиректы не настроили.

```
GET /product/pp-v-rul-58mm-new-600/  → 404
GET /shop/                           → 404
GET /category/honda-753909/          → 404
```

**Как влияет.** 780 из 1 000 проверенных адресов в отчёте 404 — старые страницы: 690 карточек
товаров, 47 страниц магазина, 22 категории. Накопленный ими вес теряется, посетители по старым
ссылкам попадают в никуда.

**Как лечить.**
1. Числовой хвост старых адресов (`-685`, `-600`, `-753909`) — тот же `id`, что используется
   сейчас, поэтому сопоставление выводится автоматически.
2. Добавить правила в `redirects()` в `frontend/next.config.js`: `/product/:slug` →
   `/{локаль}/product/:slug/`, аналогично для `/category/:slug` и корневых `/shop`, `/about`,
   `/terms`, `/contact`, `/discounts`.
3. Ставить `permanent: true` — временный редирект не передаёт вес.
4. Для отсутствующих товаров — см. T-9.

**Проверка.** Старый адрес отвечает 308 и приводит на рабочую страницу.

## T-2. Склеить www.airbagad.com с основным доменом
**754 URL**

**Проблема.** Поддомен `www` отдаёт полную копию сайта вместо редиректа.

```
GET https://www.airbagad.com/  → 302 https://www.airbagad.com/uk/   (остаётся на www)
```

**Как влияет.** 228 из 342 записей «канонический вариант не выбран», 248 из 326 «вариантов
с canonical», 278 из 1 000 записей 404. Вес делится между двумя копиями. Директива `Host`
в `robots.txt` не работает — Google её не поддерживает.

**Как лечить.**
1. На Cloudflare или nginx перед приложением — безусловный 301 с `www.airbagad.com/*`
   на `airbagad.com/$1` с сохранением пути и query.
2. Правило ставится до приложения, внутри Next.js это делать не нужно.
3. Убрать директиву `Host` из `frontend/src/app/robots.js`.

**Проверка.** `curl -I` по адресу на www возвращает 301, а не 200.

## T-3. Привести sitemap.xml к тому же виду адресов, что и сайт
**419 URL**

**Проблема.** В `next.config.js` включено `trailingSlash: true`, а карта сайта перечисляет
адреса без завершающего слэша — слэш срезается в `frontend/src/utils/seo.js:47`
(`.replace(/\/$/, '')`).

```
sitemap.xml:  /ru/product/pp-v-remeni-mikropulki-469   → 308
canonical:    /ru/product/pp-v-remeni-mikropulki-469/
```

**Как влияет.** 334 из 335 записей «Страница с переадресацией» — это они. Карта сайта
противоречит каноническим адресам в HTML.

**Как лечить.**
1. В `frontend/src/app/sitemap.js` добавлять слэш и в `url`, и во все `alternates.languages`,
   включая `x-default`.
2. В `buildAlternates()` убрать срезание слэша.
3. Вынести сборку адреса в одну функцию, чтобы карта сайта и метатеги не разошлись снова.

**Проверка.** Любой `<loc>` отвечает 200 без промежуточного редиректа.

## T-4. Устранить конфликт основной языковой версии
**292 URL**

**Проблема.** Основная локаль задана в двух местах по-разному.

```
src/i18n.js:4        defaultLocale = 'ru'   → sitemap перечисляет /ru/…
src/middleware.js:9  defaultLocale: 'uk'    → сайт ведёт на /uk/
```

Дополнительно в проекте два файла middleware: `frontend/middleware.js` и
`frontend/src/middleware.js` с разными настройками.

**Как влияет.** Google берёт из карты сайта русские адреса, а навигация ведёт на украинские.
Все 292 записи «Обнаружена, не проиндексирована» — русские, без единого `uk` или `en`.

**Как лечить.**
1. Выбрать основную локаль (логично `uk`: бизнес украинский, редирект уже ведёт туда,
   контент на украинском).
2. Оставить один middleware, читающий настройки из `src/i18n.js`; второй удалить.
3. Поправить `defaultLocale` в `i18n.js` — карта сайта и `x-default` подтянутся сами.
4. Заменить редирект с главной с 302 на 301.

**Проверка.** `x-default`, цель редиректа с `/` и настройка в коде указывают на одну локаль.

# P1

## T-5. ~~Вернуть теги hreflang в HTML страниц~~ — снята, ложная находка

Первоначально задача утверждала, что hreflang не рендерится. Это неверно: Next выводит
атрибут как `hrefLang`, и проверка `grep` по строчному `hreflang` его не находила.
HTML-парсеры к регистру атрибутов нечувствительны, поэтому Google теги читает.

```
https://airbagad.com/uk/shop/
<link rel="alternate" hrefLang="en" href="https://airbagad.com/en/shop/"/>
<link rel="alternate" hrefLang="ru" href="https://airbagad.com/ru/shop/"/>
<link rel="alternate" hrefLang="uk" href="https://airbagad.com/uk/shop/"/>
<link rel="alternate" hrefLang="x-default" href="https://airbagad.com/ru/shop/"/>
```

Настоящие дефекты в этой области — отсутствие тегов на страницах без `buildAlternates`
(T-6) и `x-default`, указывавший на `ru` вопреки редиректу на `uk` (T-4). Оба исправлены.
За 211 записей «canonical Google и сайта не совпадают» отвечает T-7 — одинаковый текст
во всех трёх языковых версиях.

## T-6. Добавить canonical на главную, «О нас» и прочие страницы без метаданных
**342 URL**

**Проблема.** Часть страниц не сообщает свой канонический адрес.

```
/uk/       → 200, canonical отсутствует
/ru/about/ → 200, canonical отсутствует

src/app/[locale]/page.jsx        generateMetadata не экспортируется
src/app/[locale]/about/page.jsx  метаданные без alternates
```

**Как влияет.** Эти адреса и составляют группу «канонический вариант не выбран пользователем».
Когда сайт молчит, выбор делает Google.

**Как лечить.**
1. Добавить `alternates: buildAlternates(path, locale)` на главную, `/about/`, `/returns/`.
2. Пройти по всем каталогам в `frontend/src/app/[locale]/` — сейчас функция подключена
   в 11 из них.

**Проверка.** Каждая индексируемая страница отдаёт ровно один canonical на себя.

## T-7. Перевести карточки товаров или сократить набор языковых версий
**211 URL**

**Проблема.** Все три локали отдают один и тот же украинский текст.

```
/ru/product/pp-v-remeni-mikropulki-469/  «ПП в ремені мікропульки»
/en/product/pp-v-remeni-mikropulki-469/  «ПП в ремені мікропульки»
```

**Как влияет.** Даже с исправным hreflang (T-5) Google склеивает дословно совпадающие страницы.
Три версии не расширяют охват, а множат дубликаты.

**Как лечить.**
1. Найти источник заголовков и описаний (поля в API `goods` и `good-categories`)
   и завести переводы на уровне данных.
2. Если перевести каталог сейчас нереально — оставить в sitemap и hreflang только языки
   с настоящим контентом, остальные закрыть от индексации.

**Проверка.** Тексты товара в разных локалях различаются либо лишние локали исключены.

## T-8. Закрыть от индексации личный кабинет и служебные разделы
**22 URL**

**Проблема.** Личный кабинет открыт роботам; во всём `frontend/src/app/` нет ни одного
`noindex`.

```
/uk/orders/   200, запрета на индексацию нет
robots.txt    закрыты:    cart, checkout, login, register, search,
                          order-success, payment-error
              не закрыты: orders, profile, cabinet, returns, compare
```

**Как влияет.** Бюджет сканирования тратится на страницы, которым нечего делать в поиске.
13 таких адресов уже в отчётах, ещё 9 помечены как заблокированные в robots.txt.

**Как лечить.**
1. Добавить `robots: { index: false, follow: false }` в метаданные `orders`, `profile`,
   `cabinet`, `returns`, `compare`, `checkout`, `cart`, `login`, `register`.
2. Дописать недостающие пути в `frontend/src/app/robots.js`.
3. Соблюсти порядок: закрытую в `robots.txt` страницу робот не читает и `noindex` в ней
   не видит. Сначала запрет в коде, после выпадения из индекса — блокировка в robots.txt.

**Проверка.** Приватные разделы исчезают из отчёта «Просканирована, но не проиндексирована».

## T-9. Определить, что происходит со снятыми с продажи товарами
**220 URL**

**Проблема.** 220 адресов в отчёте 404 уже в новой структуре — это товары, удалённые после
переезда. Единой политики нет.

```
/ru/product/pp-v-remni-tampony-rovnye-bez-usov-176/  → 404
/ru/product/mercedes-gle-19-shkira-316/              → 404
```

**Как влияет.** Google месяцами возвращается к удалённым адресам, посетитель попадает
на пустую страницу вместо аналога. Плюс `fetchAll('goods')` в `sitemap.js` берёт всё, что
отдаёт API, без фильтра по статусу публикации.

**Как лечить.**
1. Товар вернётся — оставить страницу с пометкой «нет в наличии», адрес не удалять.
2. Есть замена — 301 на аналог или категорию.
3. Замены нет — отдавать `410 Gone`: такие адреса Google убирает из очереди быстрее, чем 404.
4. Добавить фильтр по статусу публикации в `fetchAll('goods')`.

**Проверка.** Удалённый товар отдаёт осознанный код ответа и отсутствует в sitemap.xml.

## T-10. Переключить навигацию на настоящие страницы категорий
**148 URL**

**Проблема.** Полноценные страницы категорий существуют и есть в sitemap (50 записей),
но ссылки на сайте ведут на магазин с параметром фильтра.

```
есть:         /ru/category/acura-753903/   «Acura | AirbagAD»
ссылки ведут: /uk/shop/?category=753922    canonical → /uk/shop/
```

**Как влияет.** Формально не ошибка — Google поступает верно. Но категорийные страницы
не получают внутренних ссылок и не набирают вес, а запросы вида «подушка безопасности Acura»
приводят на общую страницу магазина.

**Как лечить.**
1. Перевести меню, карусель категорий и фильтры на `/{локаль}/category/{slug}-{id}/`.
2. `?category=` оставить только как состояние фильтра внутри магазина.

**Проверка.** Категорийные страницы получают внутренние ссылки и появляются в индексе.

## T-11. Разобраться с пустыми страницами английской версии
**6 URL**

**Проблема.** Шесть адресов помечены как «ложная ошибка 404» — отвечают 200, но выглядят
пустыми. Все шесть в локали `en`.

```
/en/car-brands/            200, контента робот не видит
/en/shop/?category=753903  200
/en/checkout/              200
```

**Как влияет.** Такие страницы выпадают из индекса целиком. Вероятная причина — контент
рендерится только на клиенте либо в английской версии данных нет.

**Как лечить.**
1. Открыть адреса через «Проверить URL» → «Посмотреть отсканированную страницу» и сравнить
   с тем, что видит пользователь.
2. Если список брендов и товаров рендерится на клиенте — перенести в серверный рендер.
3. `/en/checkout/` закрывается в рамках T-8.

**Проверка.** В отсканированной версии страницы виден основной контент.

## T-12. Через месяц пересобрать данные и оценить остаток
**694 URL**

**Проблема.** Крупнейшая категория после 404: 551 карточка товара и 108 страниц магазина.
Отдельной технической причины нет — так помечаются страницы, которые Google счёл
недостаточно ценными или дублирующими.

**Как влияет.** Основная часть должна уйти после T-2, T-5 и T-7. Что останется — и есть
настоящая проблема содержания карточек. Здесь же 12 адресов `/_next/static/media/*.woff2`
(и ещё 5 в отчёте 404) — попадают в обход из-за ссылок с домена www, уйдут вместе с T-2.

**Как лечить.**
1. Выложить T-1 – T-9, подождать 2–4 недели.
2. Снять отчёт заново, сравнить с таблицей выше.
3. Остаток разбирать как задачу о качестве описаний, а не техническую.

**Проверка.** Категория сократилась пропорционально снятым дублям.

## Что проверить после выкладки

- [ ] Старый адрес WooCommerce, адрес на www, адрес из sitemap и главная отвечают нужными
      кодами и приводят на рабочие страницы.

- [ ] Личный кабинет и оформление заказа закрыты от индексации.
- [ ] В GSC по каждой причине нажата «Проверить исправление» (занимает от нескольких дней
      до двух недель).
- [ ] Через 30 дней отчёт снят заново и сравнён с исходными цифрами.
