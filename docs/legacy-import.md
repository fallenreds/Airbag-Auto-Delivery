# Перенос данных из старого бота в новую систему

Старая версия (ветка `master`, боевая до сих пор) хранит всё в одном SQLite-файле
`AirbagDatabase.db`. Новая (`v2`) — в Django-моделях `core_*`. Схемы несовместимы:
заказ там держал состав одной строкой питоновского `repr`, клиент — пароль
открытым текстом, суммы — в гривнах, а не в копейках.

Переносит данные management-команда
[`import_legacy_db`](../backend/core/management/commands/import_legacy_db.py).

## Как запускать

```bash
cd backend

# 1. Превью — база не меняется, печатается «что и сколько приедет»
python manage.py import_legacy_db /path/AirbagDatabase.db

# 2. Резервная копия перед записью
cp db.sqlite3 db.sqlite3.bak-$(date +%Y%m%d)

# 3. Запись
python manage.py import_legacy_db /path/AirbagDatabase.db --apply
```

Превью — режим по умолчанию: без `--apply` не пишется ничего. Считается оно не
«на глаз», а настоящей записью внутри транзакции, которая затем откатывается —
поэтому цифры превью совпадают с боевым прогоном (это проверяется тестом).

### Флаги

| Флаг | Зачем |
|---|---|
| `--apply` | действительно писать в базу |
| `--only clients,orders` | часть секций: `clients`, `orders`, `carts`, `discounts`, `templates`, `visitors` |
| `--since 2026-01-01` | только заказы не раньше даты |
| `--limit-orders 50` | пробный прогон на последних N заказах |
| `--with-passwords` | перенести пароли (в старой базе они открытым текстом; по умолчанию пароль ставится неиспользуемым) |
| `--verbose-skips` | печатать каждую пропущенную запись, а не только сводку |

Импорт **идемпотентен**: повторный запуск на той же базе ничего не дублирует.
Можно гонять по секциям, править и повторять.

## Что во что переезжает

| Старая таблица | Новая модель | Примечания |
|---|---|---|
| `client` | `Client` | телефон нормализуется к `+380XXXXXXXXX`; почты у старых клиентов нет |
| `orders` | `Order` | `date` восстанавливается отдельным UPDATE — у поля `auto_now_add` |
| `orders.goods_list` | `OrderItem` | строка `repr` разбирается; `good_id` — это remonline-id товара |
| `shopping_cart` | `Cart` + `CartItem` | группируется по `telegram_id` |
| `discounts` | `Discount` | `month_payment` умножается на 100 (гривны → копейки) |
| `template` | `Template` | |
| `visitors` | `BotVisitor` | |
| `client_updates`, `order_updates` | — | очереди событий, переносить нечего |

## Решения, которые стоит знать

- **Новая база — источник истины.** Если клиент уже есть (совпал `telegram_id`,
  затем `id_remonline`, затем телефон), импорт только дополняет **пустые** поля
  и никогда не перебивает заполненные.
- **Даты старой базы — UTC.** Старый бот писал их через SQLite `datetime('now')`,
  а это UTC без таймзоны.
- **Заказы приезжают со статусом `SYNCED`.** Они уже заведены в RemOnline, и
  `PENDING` заставил бы систему завести дубли.
- **Суммы восстанавливаются по текущему прайсу.** Старый заказ не хранил ни
  итога, ни скидки, поэтому `grand_total` равен `subtotal`, а `discount_percent`
  остаётся пустым. Историческая аналитика по деньгам из этих чисел
  недостоверна — это оценка, а не факт.
- **Пароли по умолчанию не переносятся.** Вход в новую систему — по почте,
  которой у старых клиентов нет; логин сохраняется как справочная информация.
- **Позиция удалённого товара сохраняется снимком** (`good=None`, title
  `Товар #<remonline id>`, цена 0) — заказ не должен терять состав из-за того,
  что товар убрали из каталога. Позиция корзины на такой товар, наоборот,
  пропускается: у `CartItem` снимка нет, только FK.
