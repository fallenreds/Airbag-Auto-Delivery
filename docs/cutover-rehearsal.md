# Репетиция переключения: что увидят пользователи

Проверка проводилась не «по коду», а прогоном: копия боевой базы новой системы,
в неё импортируется **живой** дамп старой (снят 26.08.2026 13:23, 3948 заказов),
затем на этих данных запускается настоящий код — фоновый обработчик, поллеры и
хендлеры бота. Telegram подменён: ни одно сообщение никуда не ушло, но всё, что
бот попытался бы отправить, посчитано.

Стенд — отдельный файл базы и отдельный модуль настроек; боевые серверы за всю
проверку только читались.

## 1. Лишние уведомления: их нет

| Источник | Что могло прилететь | Результат |
|---|---|---|
| `order_event_handler` (раз в минуту) | «Дякуємо за замовлення», «ваш ТТН», «прибуло у відділення», автоотмена | **0 событий** на 16 активных импортированных заказов |
| `get_no_paid_orders` (раз в час) | «у вас є несплачені замовлення» | **0 сообщений** |
| `client_updates` | «новий користувач» админам | **0 событий** (импортёр их не создаёт) |
| Очередь `OrderEvent` | всё вышеперечисленное | **пуста** |

Ноль в первой строке — не случайность: обработчик реально сходил в RemOnline по
всем 16 заказам и сравнил стадии. Расхождений не нашлось, поэтому и событий не
возникло.

### Чего это стоило

Тот же импорт **без сверки с RemOnline** (`--no-remonline-check`) на дампе
двухдневной давности даёт **11 событий `FINISHED` — 11 человек получают
«Дякуємо за замовлення» повторно**, потому что старая система уже сказала им
это, а в устаревшем дампе заказы ещё числились открытыми.

Отсюда два вывода, оба уже учтены: сверка включена по умолчанию, а дамп надо
снимать в момент переключения. На свежем дампе сверке чинить нечего — она
закрыла 0 заказов.

## 3. Скидки не поменяются ни у кого

Старая система считала сумму прошлого месяца по **текущим** ценам RemOnline
(`engine.get_month_money_spent` берёт живой кеш товаров) — ровно так же, как это
делает импортёр. Проверено повторением старой формулы на тех же данных:

```
сверено клиентов: 173
  совпало:        173
  разошлось:        0

распределение в старой: {0%: 156, 2%: 8, 4%: 5, 6%: 3, 8%: 1}
распределение в новой:  {0%: 156, 2%: 8, 4%: 5, 6%: 3, 8%: 1}
```

Семнадцать человек со скидкой сохраняют её до процента.

## 4. Вход каждого пользователя

Для всех 174 клиентов с привязанным Telegram прогнаны настоящие хендлеры бота —
те самые, что сработают при нажатии кнопки:

```
проверено пользователей: 174

«Статус замовлень 📦»
  показал заказы:            15      ← ровно столько, сколько ожидалось
  «немає замовлень»:        159
  «не авторизовані»:          0      ← бот узнал каждого
  упало с ошибкой:            0

«Знижки 💎»
  ответил корректно:        174
  ошибок:                     0

сообщений на пользователя за оба нажатия: ровно 2

Проблем не найдено.
```

Ни одного «Ви не авторизовані» — то есть импортированные клиенты опознаются
ботом с первого нажатия, ничего заново подключать им не нужно.

## 5. Рассылка приглашений

С подменённым Telegram, 170 получателей:

```
первый прогон:     отправлено 158, бот заблокирован 12
повторный прогон:  уже отправляли 158, бот заблокирован 12

сообщений одному человеку: ровно 1
```

Заблокировавшие бота не считаются ошибкой и повторяются в следующий раз —
человек мог разблокировать.

## Что осталось за рамками проверки

- **Стадии, которых нет в старой базе.** Отмена заказа, запрос на отмену,
  возврат, оплата по реквизитам — этого в старой системе не было вообще,
  переносить нечего. Импортированные заказы приезжают с пустым `cancel_state`.
- **Живой Telegram.** Ни одно сообщение в ходе репетиции не отправлялось.
  Первая настоящая проверка в боте — после переноса токена, на своём аккаунте.
- **Три «висяка»** от июня–июля без ТТН и без номера в RemOnline. Они не
  попадают в обработчик (тот требует `remonline_order_id`), уведомлений не
  породят, но и не закроются сами — их стоит закрыть руками.
